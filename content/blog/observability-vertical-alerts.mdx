You've got metrics flowing from Part 1. Now the question is: **who gets woken up at 2am when something breaks?**

Before writing a single alert rule, it's worth separating two concerns that are often conflated in observability setups:

### The alerting platform

The routing infrastructure that exists once. PagerDuty service, escalation policy, Grafana contact points, notification policy. This is owned by whoever runs the observability stack. It doesn't change when a new service or device is onboarded. It answers the question: *when something fires, who gets paged and how?*

### Service alert rules

What fires. Each service, device, or application that joins the network owns its own alert definitions as part of its own infrastructure-as-code. A Raspberry Pi, a web service, a database — each defines what "unhealthy" means for itself, and provisions those rules against the shared platform. This is covered in Part 2.5.

This separation matters more than it initially seems. In immature setups, alert rules accumulate in a single central repo owned by the platform team, creating a bottleneck: every team that wants to add or tune an alert raises a PR against someone else's repository. In the model this series uses, the platform team publishes the routing contract once, and service teams own their own alert definitions independently.

This post covers the platform layer only — the plumbing that routes any alert that fires to the right person on call.

---

## The alerting platform contract

The platform exposes one thing to service teams: **a Grafana instance with a configured notification policy and a PagerDuty contact point**. Any alert rule provisioned against this Grafana — regardless of which service's Terraform created it — will be routed to PagerDuty according to the notification policy.

The contract is:

- Alerts labelled `severity = critical` → immediate page, repeats hourly
- Alerts labelled `severity = warning` → 1 minute buffer, repeats every 8 hours
- Alerts must include `alertname` and `instance` labels for proper incident grouping

That's it. Service teams don't need to know about PagerDuty integration keys, escalation policies, or routing logic. They write alert rules, label them with a severity, and the platform handles the rest.

```
Any alert rule (from any service's Terraform)
              │
           Grafana
        (notification policy)
              │
    ┌─────────┴──────────┐
    │                    │
  warning             critical
  8h repeat           1h repeat
    │                    │
    └─────────┬──────────┘
              │
    PagerDuty contact point
              │
    PagerDuty service + escalation policy
              │
         On-call engineer
```

## Providers

`main.tf`:

```hcl
terraform {
  required_version = ">= 1.0"
  required_providers {
    grafana = {
      source  = "grafana/grafana"
      version = "~> 3.0"
    }
    pagerduty = {
      source  = "PagerDuty/pagerduty"
      version = "~> 3.0"
    }
  }
}

provider "grafana" {
  url  = var.grafana_url
  auth = "${var.grafana_admin_user}:${var.grafana_admin_password}"
}

provider "pagerduty" {
  token          = var.pagerduty_token
  service_region = var.pagerduty_service_region
}

locals {
  pagerduty_enabled = var.pagerduty_token != ""
}
```

## PagerDuty module

The PagerDuty module creates a dedicated service for infrastructure monitoring, wires a Grafana integration to it, and outputs the integration key so the Grafana contact point can reference it.

`modules/pagerduty/main.tf`:

```hcl
# Reference your existing user and default escalation policy
data "pagerduty_user" "me" {
  email = var.pagerduty_user_email
}

data "pagerduty_escalation_policy" "default" {
  name = "Default"
}

resource "pagerduty_service" "infra" {
  name                    = "Infrastructure Monitoring"
  auto_resolve_timeout    = 14400   # auto-resolve after 4 hours if no further data
  acknowledgement_timeout = 600     # re-alert after 10 minutes if not acknowledged

  escalation_policy = data.pagerduty_escalation_policy.default.id
  alert_creation    = "create_alerts_and_incidents"
}

# Events API v2 integration — supports severity-based deduplication in PagerDuty
resource "pagerduty_service_integration" "grafana" {
  name    = "Grafana"
  service = pagerduty_service.infra.id
  type    = "events_api_v2_inbound_integration"
}

output "integration_key" {
  value     = pagerduty_service_integration.grafana.integration_key
  sensitive = true
}
```

`modules/pagerduty/variables.tf`:

```hcl
variable "pagerduty_user_email" {
  type = string
}
```

Invoke it conditionally in `main.tf` — the same config works with email-only when PagerDuty isn't configured:

```hcl
module "pagerduty" {
  count  = local.pagerduty_enabled ? 1 : 0
  source = "./modules/pagerduty"

  pagerduty_user_email = var.pagerduty_user_email
}
```

## Contact points

Two contact points — PagerDuty when configured, email as fallback. Only one is active at a time based on whether `pagerduty_token` is set.

```hcl
resource "grafana_contact_point" "email" {
  count = local.pagerduty_enabled ? 0 : 1
  name  = "Email Notifications"

  email {
    addresses = [var.alert_email]
  }

  lifecycle {
    create_before_destroy = true
  }
}

resource "grafana_contact_point" "pagerduty" {
  count = local.pagerduty_enabled ? 1 : 0
  name  = "PagerDuty On-Call"

  pagerduty {
    integration_key = module.pagerduty[0].integration_key
    severity        = "critical"
    # Go template — renders the firing alert names directly in the PagerDuty incident title
    summary = "{{ len .Alerts.Firing }} alert(s): {{ range .Alerts.Firing }}{{ .Labels.alertname }} {{ end }}"
  }

  lifecycle {
    create_before_destroy = true
  }
}
```

The `summary` template means the PagerDuty incident title immediately tells you what's wrong — "2 alert(s): NodeDown ContainerOOMKill" — without needing to open Grafana first.

## Notification policy

This is the core of the platform — the routing logic that every alert rule in the system flows through. It lives here and nowhere else.

```hcl
resource "grafana_notification_policy" "main" {
  group_by      = ["alertname", "instance"]
  contact_point = local.pagerduty_enabled ? grafana_contact_point.pagerduty[0].name : grafana_contact_point.email[0].name

  # Default: buffer for 30s to group related alerts, repeat every 4h
  group_wait      = "30s"
  group_interval  = "5m"
  repeat_interval = "4h"

  # Critical — immediate page, repeats hourly until resolved
  policy {
    matcher {
      label = "severity"
      match = "="
      value = "critical"
    }
    contact_point   = local.pagerduty_enabled ? grafana_contact_point.pagerduty[0].name : grafana_contact_point.email[0].name
    group_wait      = "0s"
    repeat_interval = "1h"
  }

  # Warning — 1 minute buffer to avoid flapping, repeats every 8 hours
  policy {
    matcher {
      label = "severity"
      match = "="
      value = "warning"
    }
    group_wait      = "1m"
    repeat_interval = "8h"
  }

  depends_on = [
    grafana_contact_point.email,
    grafana_contact_point.pagerduty,
  ]
}
```

A few decisions worth understanding:

`group_by = ["alertname", "instance"]` — without `instance`, alerts from all hosts collapse into a single PagerDuty incident. With it, each host gets its own incident grouping so it's immediately clear which machine is the problem.

`group_wait = "30s"` at the top level — when a node goes down it often triggers several alerts simultaneously (NodeDown, HighMemory, LowDisk if the disk was filling). The 30-second buffer lets them group into a single notification. The critical policy overrides this to `0s` so a node going offline pages immediately — the grouping still happens, just without the artificial delay.

`repeat_interval` — critical alerts repeat hourly until resolved because an unresolved critical means something is actively broken. Warning alerts repeat every 8 hours because they represent degradation, not failure, and you don't want to be woken up repeatedly for something that can wait until morning.

## Applying the platform

```bash
cp terraform.tfvars.example terraform.tfvars
# Fill in credentials

terraform init
terraform plan
terraform apply
```

Verify contact points and policy were created:

```bash
# Contact points
curl -s http://localhost:3000/api/v1/provisioning/contact-points \
  -u admin:changeme \
  | jq '.[].name'

# Notification policy
curl -s http://localhost:3000/api/v1/provisioning/policies \
  -u admin:changeme \
  | jq '.receiver'
```

At this point the platform is ready. No alert rules exist yet — those are provisioned by each service in Part 2.5. But the routing contract is in place: any rule that fires against this Grafana will reach PagerDuty.

## Testing the routing without real alerts

Before service alert rules exist, you can verify the end-to-end path by sending a test alert directly to Grafana's API:

```bash
curl -s -X POST http://localhost:3000/api/v1/alerts \
  -u admin:changeme \
  -H 'Content-Type: application/json' \
  -d '[{
    "labels": {
      "alertname": "TestAlert",
      "severity": "critical",
      "instance": "test-host"
    },
    "annotations": {
      "summary": "Platform routing test"
    },
    "startsAt": "'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'"
  }]'
```

This injects a synthetic firing alert. If PagerDuty is configured, an incident should appear within seconds. If using email, check your inbox. Either way, you've confirmed the routing path before any service is onboarded.

Resolve it by sending the same payload with an `endsAt` field:

```bash
curl -s -X POST http://localhost:3000/api/v1/alerts \
  -u admin:changeme \
  -H 'Content-Type: application/json' \
  -d '[{
    "labels": {
      "alertname": "TestAlert",
      "severity": "critical",
      "instance": "test-host"
    },
    "endsAt": "'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'"
  }]'
```

## Silencing alerts

Once a firing alert is a known issue being worked on, silences suppress notifications for a time window without disabling the rule.

Via the Grafana UI: Alerting → Silences → Add silence. Set a matcher, an expiry, and a comment with the incident or ticket number.

Via the API — useful when you're remediating something and want to silence from the terminal:

```bash
curl -s -X POST http://localhost:3000/api/v1/silences \
  -u admin:changeme \
  -H 'Content-Type: application/json' \
  -d '{
    "matchers": [
      { "name": "instance", "value": "my-server", "isRegex": false }
    ],
    "startsAt": "'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'",
    "endsAt":   "'"$(date -u -d '+2 hours' +%Y-%m-%dT%H:%M:%SZ)"'",
    "comment":  "Maintenance window — deploying new disk",
    "createdBy": "on-call"
  }'
```

Silencing by `instance` rather than `alertname` suppresses all alerts from a specific host — useful during maintenance without having to list every possible alert name.
